Part 1 · Failure clinicIs the number real?

The situation. In the neural-network lab a hidden layer beat the best straight line by about 0.03 NDCG@10. Three students report improvements of that size after changing something. None of them can say whether it is real.

Questions to ask before believing a gain

  • Same exam, same split, same seed?
  • Did a row appear twice, once in the training part and once in the exam?
  • Is any timestamp wrong, so that "the past" contains the future?
  • Does any column exist that the live app would not have?

Why this is a data question

A model can only be as honest as its table. Cleaning mistakes do not raise errors: they raise scores.

A duplicated event, a 1970 timestamp or a column that knows the future never crashes a notebook. It just changes the number you report.

Before arguing about models, argue about the table.

  • Use a real case from the demos if one fits: a result that was too good, or a gap too small to trust.
  • Do not give the answers yet. Ask the room which of the four questions they would check first, then tell them that the next slides show how each of them goes wrong.

Part 2 · Theory · 1 of 9Why real event logs are dirty

Nobody makes a log dirty on purpose. It happens because many programs write it, and programs fail in ordinary ways.

Where it comes fromWhat it leaves in the log
Retries after a timeoutThe same event twice, a few seconds apart
Half-written requestsRows with a missing user or rating
Different clients, different conventionsSeconds here, milliseconds there, date text elsewhere; "4,5" instead of 4.5
Clocks and default valuesTimestamps in 1970 (the value 0) or in the future
Deleted or renamed thingsEvents about an item that no longer exists
Exports built for dashboardsColumns computed from the whole history, which contain the future

Each row of this table is exactly one thing the Colab breaks and then repairs.

  • The Colab's damage script is deterministic (seed 42) and every damage is either fixable or an extra row to discard. That is what makes a perfect cleaning possible, and testable, in a classroom.
  • Ask for one example from a student's own experience: a duplicate payment, a notification sent twice.

Part 2 · Theory · 2 of 9pandas in one page: six moves and what each one gives back

df is a variable name for a table, as in df = pd.read_csv("raw_events.csv"). Here it is a 4-row toy:

user_idratingts

None of the six commands below changes df. Each one returns something new (a value, a column, or a new table). df changes only when you assign the result back: df = ... replaces the whole table, df["col"] = ... adds or replaces one column. (inplace=True exists, but avoid it.)
CommandWhat it returns for the toy tableTo keep the result
df.dtypesthe type of each column: int64, float64, int64nothing: it is information
df.isna().sum()missing values per column: 0, 1, 0nothing: it is information
df[df["rating"] >= 4.0]a new table with rows 0 and 2 (df still has 4 rows)df = df[df["rating"] >= 4.0]
df["ts"].between(1000, 2000)one True/False per row: T, T, T, Fused as the filter: df = df[df["ts"].between(1000, 2000)]
df.groupby("user_id").cumcount()a column 0, 1, 0, 1: how many rows of the same user came beforedf["n_before"] = df.groupby("user_id").cumcount()
df.sort_values("ts")a new table, same rows in the order 3, 0, 2, 1df = df.sort_values("ts")

The most common beginner surprise: you run a pandas command, nothing seems to happen, because you did not keep the result.

  • Run the first line of the table in your head with the toy table: df[df["rating"] >= 4.0] prints a 2-row table, and the next line df still shows 4 rows. NaN compared with 4.0 is False, so row 3 is dropped too.
  • Two kinds of "keeping": df = ... rebinds the name to the new table; df["n_before"] = ... modifies the existing table by adding a column. The Colab uses both.
  • Four habits worth more than any function: look before touching (shape, dtypes, a random sample); count rows before and after every step that removes rows; sort explicitly before anything that depends on order; never edit the raw file, keep raw and clean in code.
  • cumcount is the pandas way of saying "how many rows of this group came before me". The Colab uses it to count a user's earlier likes, then checks the result against the code that built the original signals.

Part 2 · Theory · 3 of 9Types and time: convert first, filter later

A numeric column that pandas shows as object or str is a column with text in it. You cannot ask whether a piece of text is "in the future".

text = col.astype(str).str.strip()
text = text.str.replace(",", ".", regex=False)
num  = pd.to_numeric(text, errors="coerce")
#                    unreadable -> NaN, no crash

secs = num.where(num < 1e11, num / 1000)
#      1e11 s would be the year 5138: it is ms

One timestamp, three forms

1332458321seconds since 1970
1332458321000milliseconds: divide by 1000
2012-03-22 22:58:41date text: pd.to_datetime(..., utc=True)

Choose one unit and one time zone (UTC) for the whole pipeline, and write it down.

errors="coerce" is the polite way to fail: the bad value becomes NaN, and the next step can count and remove it.

  • Without coerce, one bad cell stops the whole conversion. With coerce, you must remember to check for NaN afterwards: that is what the Colab's Step 2 does.
  • The 1e11 rule is a heuristic with a stated reason: it works for dates between 1973 and 5138. Say that heuristics need a written reason.

Part 2 · Theory · 4 of 9A twelve-row log, cleaned one step at a time

What you see. Press 0 to 6 to apply the cleaning steps in order. Struck-out rows are removed, with the reason; gold cells were repaired.

The Colab does exactly this on 107 388 rows. Here you can see every row.

  • Predict first. At each step ask how many rows will remain, then press the button.
  • Step 1 removes nothing, yet it repairs rows 2, 4 and 11 (the gold cells). Rows 6 and 7 get a NaN there: that is how step 2 finds them.
  • Rows 6, 7 and 8 are all bad copies of the same real event (row 9). Dropping them loses nothing. Say that this is a property of this log, not a rule: if the copies were the only record, dropping them would lose data.
  • End state: five rows. In the Colab the same steps take 107 388 rows to 100 836, which is exactly the original table.

Part 2 · Theory · 5 of 9Joins: find the rows that point to nothing

A merge glues two tables on a shared column, like a SQL JOIN. Question: which events talk about a movie that is not in the movies table?

df (events)

user_iditem_id
17296
17318
23999999

movies

item_idtitle
296Pulp Fiction
318Shawshank
checked = df.merge(movies, on="item_id",
                   how="left",        # keep every event, even without a match
                   indicator=True,    # add a column _merge: matched or not
                   validate="m:1")    # each item must appear once in movies
df = checked[checked["_merge"] == "both"]   # keep the matched rows

checked (a new table; df is unchanged until the last line):

user_iditem_idtitle_merge
17296Pulp Fictionboth
17318Shawshankboth
23999999NaNleft_only
Why validate="m:1"? If movies listed item 296 twice, a merge would silently produce two rows for each event on 296 and inflate every count after it. With validate, pandas stops with an error instead.

A merge is a lookup: for every event, find its movie. how="left" says: keep every event, even if nothing matches.

  • The row with item 999999 has no match: the title is NaN and _merge says left_only. Filtering on _merge == "both" keeps only the events that point to something real.
  • In the Colab this removes 504 events about items that do not exist.
  • validate="m:1" reads "many events to one movie". It checks an assumption you would otherwise only discover when your counts look inflated.

Part 2 · Theory · 6 of 9Duplicates: two problems, two operations

A log repeats itself in two ways. The same toy df goes through two steps; in each table, the red row is the one that step removes.

1 · Exact repeats (input: 4 rows)

df = df.drop_duplicates()
# drops a row equal to an earlier
# row in EVERY column
useritemratingts
825714.01230788250first write
825714.01230788250exact repeat ← removed
825714.01230788270retry, 20 s later
9503.51230790000

2 · Retries (input: 3 rows)

df = df.sort_values("ts")
df = df.drop_duplicates(
    subset=["user_id", "item_id"])
useritemratingts
825714.01230788250first write
825714.01230788270retry, 20 s later ← removed

Result (2 rows)

one row per (user, item): the earliest.
useritemratingts
825714.01230788250first write
9503.51230790000
Step 1 finds rows that are identical in every column. Step 2 looks only at the columns in subset: the retry differs in ts, but it is the same (user, item) event. After sorting by ts, the first row of each pair is the earliest; drop_duplicates keeps the first and drops the rest.
Check the assumption first. "Keep the earliest" is only safe if retries never change the value: 
pairs = df.groupby(["user_id", "item_id"])
assert pairs["rating"].nunique().max() == 1

Two different problems that people call by the same name. Exact repeats are identical rows; retries are the same event written again a little later.

  • First table: the second row is a byte-for-byte repeat of the first, and the third row is a retry 20 seconds later. Step 1 removes only the exact repeat (the retry differs in ts). Step 2 compares only (user, item): the first and the retry are the same pair, so after sorting by ts the earlier one stays.
  • sort_values matters: drop_duplicates keeps the first row in the current order, so without the sort you would keep whichever row happened to come first in the file.
  • The assert is the point of the slide: "keep the earliest" is a rule with an assumption. If a retry had a different rating, which one is right? There is no pandas answer, it is a product decision. The assert makes the question visible instead of buried.
  • In the Colab: 2 016 exact repeats, then 1 512 retries, ending at exactly 100 836 rows.

Part 2 · Theory · 7 of 9The order of the steps matters

What you see. Three rows are one real event of user 8: the event, a bad copy with ts = 0, and a retry. Two pipelines run the same two operations in a different order. Press Step 1, then Step 2, and compare the tables.

Each step assumes the previous ones did their job. Write the steps in the order in which their assumptions become true.

  • Predict first: before pressing Step 2, ask which row will survive in each pipeline.
  • "Keep the earliest" assumes timestamps are meaningful. A timestamp of 0 is the earliest possible, so it always wins. In pipeline B it wins, and then the filter removes it: the user's like is gone, without an error message.
  • In the Colab a cell runs the wrong order on the whole log: 504 events end up with a wrong timestamp (or vanish, depending on what you do next).
  • Rule of thumb: types, then validity, then references, then duplicates.

Part 2 · Theory · 8 of 9A feature must be computable at prediction time

Temporal leakage is the most expensive data bug in machine learning, because it makes results better, not worse. One real row: on 22 October 2017 user 159 likes (500) Days of Summer. That moment is t. How many likes does that movie have?

before t: 22 likes
t: this like (1)
after t: 3 likes
item_prior_likes = 22
✓ the app can compute it at t
item_total_likes = 22 + 1 + 3 = 26
✗ needs the whole log: it contains the like we predict and 3 future ones

Not to scale. Both columns are "the number of likes of the item"; they differ only in which part of the timeline they read.

Allowed

Built from rows before t: cumcount(), counts over a window that ends at t.

Forbidden

Totals over the whole log, a "final status", any column exported after t.

The test

Could the live app compute this exact number at time t? Recompute a few values from only the earlier rows and compare.

Ask of every column: could the live app know this at the moment it must decide?

  • Come back to the exam example from the clinic: the (500) Days of Summer row. 26 = 22 + this like + 3 later. Scorer A was better only because of the 4 extra likes it should not know about.
  • Link to the feed lab: it had a leakage check (the feed must not change when future events are added). Today's Colab applies the same idea to a whole table.
  • The Colab verifies it three ways: pandas recomputes activity, age, freshness and lifetime independently and compares them with the neural-network lab code; every candidate must exist before its moment; and a slow plain-Python loop recomputes a few item_prior_likes.
  • The bar is not to scale on purpose: the point is which part of the timeline each column reads.

Part 2 · Theory · 9 of 9Reproducible: the same input must give the same table

1 · Fixed seeds

Every random choice uses a seed, so the exam is the same on every run and scores can be compared.

rng = np.random.default_rng(42)
negatives = rng.integers(0, n_items, 99)

Without the seed: a different set of 99 random items on every run.

2 · An audit trail

Rows before and after every step. If a step suddenly removes ten times more, you see it.

2. drop incomplete rows    107,388 -> 105,876  (1,512 removed)
3. drop impossible ts      105,876 -> 104,868  (1,008 removed)
4. drop unknown items      104,868 -> 104,364    (504 removed)

3 · An answer key

The Colab broke the data itself, so it can check the cleaned log equals the original, row for row.

pd.testing.assert_frame_equal(CLEAN, EXPECTED)

Real pipelines rarely have one: check a small sample by hand instead.

4 · A fingerprint

A hash of the final table: same hash, same table. Round floats first.

text = table.to_csv(index=False,
                    float_format="%.6f")
hashlib.sha256(text.encode()).hexdigest()

Reproducible does not mean "it ran on my laptop". It means someone else gets the same bytes.

  • Seeds: the exam picks 99 random items per question. With seed 42 every student gets the same exam, so a score is comparable with a classmate's.
  • Audit trail: the three lines are the real output of the Colab. The whole table is printed at the end of the notebook.
  • Answer key: say plainly that the Colab can do this only because it broke the data itself. A real project has no answer key, so you test assumptions and hand-check samples.
  • Fingerprint: the reference starts with 977334c6. It was checked on two stacks (pandas 2.2.3 with NumPy 1.26, and pandas 3.1.1 with NumPy 2.5) and was identical. If a student's hash differs but every self-check passes, the likely cause is a library version; the table is usable, ask them to note their versions.
  • Later analyses start from this table. If hashes match, results are comparable across the class.

1 · Count
